# DCT verification dataset v1

**474 immutable synthetic float32 arrays**, covering square sizes 8,16,32,64,128,256. Of these,420 are core cases and54 are boundary diagnostics. These are verification inputs, not training images. License: **CC BY 4.0**; Python tools: **BSD-3-Clause**.

## Use the data

The published data archive contains `inputs.npz`, `manifest.json` and these tools. A source-code checkout can recreate the archive:

```sh
python dataset/prepare.py
python dataset/verify.py
```

From a standalone dataset release, use `python prepare.py` and `python verify.py` instead. NumPy is the only dependency for generation and byte verification.

```python
from pathlib import Path
import json
import numpy as np

root = Path("dataset")
manifest = json.loads((root / "manifest.json").read_text())
with np.load(root / "inputs.npz", allow_pickle=False) as inputs:
    case = manifest["cases"][0]
    image = inputs[case["id"]]
```

Arrays are little-endian float32, row-major, and indexed by stable case IDs. The manifest records size, family, core/diagnostic domain, random seed where applicable, and SHA256 of the raw array bytes. `verify.py` checks the archive and every array, not just the number of files.

The reference archive SHA256 is:

`f091e39ad8e2f1f9fb3325d379a6e3953f1619b3930d3a3e7241a7ed7800b7cf`

Regeneration uses fixed seeds and ZIP timestamps. Other NumPy/math/compression versions may change regenerated bytes. A mismatch is reported, not hidden by replacing the expected hash. Use the published archive as the immutable reference in that case.

## Evaluate BRiDCT

After compiling the library, from the source-package root (use `build/libbridct.so` on Linux or `build/bridct.dll` on Windows; the command below is for macOS):

```sh
python dataset/evaluate.py --library build/libbridct.dylib --output /tmp/bridct-new-evaluation
```

The output directory must be new. The evaluator checks each direction separately against a float64 cosine-matrix oracle, input immutability and output sentinels. It saves every case, including failed boundary diagnostics. `summary.json` reports **1260 core checks and 162 boundary checks** for one selected route per size/direction. These are separate from the paper’s historical 11760-core-check multi-variant audit.

Expected behavior is a passing core gate with documented boundary failures, not an all-input pass. New evaluations write results into the explicitly selected output directory; historical evaluations are in the separate measurements archive. See the [dataset card](DATASET_CARD.md) for the contract, families and limitations. Another DCT can use the same input archive and normalization, with a replacement adapter; do not change or renormalize the stored inputs silently.
